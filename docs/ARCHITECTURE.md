# Архитектура backend

## Состав

```text
┌───────────────┐          HTTP + WebSocket          ┌─────────────────┐
│ React + Vite  │ ────────────────────────────────> │ Go API (chi)    │
│ TanStack Query│ <──────────────────────────────── │ api / auth     │
└───────────────┘                                   ├─────────────────┤
                                                    │ GORM            │
                                                    │ Local storage   │
                                                    │ WebSocket Hub   │
                                                    └───────┬────┬────┘
                                                            │    │
                                                    PostgreSQL   Volume
```

Папки и обязанности:

| Пакет | За что отвечает |
|---|---|
| `cmd/server` | Точка входа, конфигурация сервера, подключение к БД, завершение процесса |
| `internal/config` | Переменные окружения и их валидация |
| `internal/model` | Структуры данных Go с отображением на таблицы GORM |
| `internal/migrations` | Версионированная SQL-схема, применяемая через Goose |
| `internal/auth` | Argon2id, серверные сессии, cookie, получение пользователя из контекста |
| `internal/httpapi` | Маршруты, DTO и HTTP-обработчики, проверка владельца |
| `internal/storage` | Физическая запись, чтение и удаление файлов по storage key |
| `internal/realtime` | Реестр активных WebSocket-соединений и доставка уведомлений |
| `internal/ratelimit` | Простейший локальный лимит попыток входа и регистрации |

## Поток создания заметки

1. Клиент отправляет `POST /api/items/text`, прикладывая cookie и `X-CSRF-Token`.
2. Middleware загружает сессию, проверяет её срок действия и устанавливает владельца в `context.Context`.
3. Handler проверяет CSRF и валидирует содержимое записи.
4. GORM сохраняет объект с `user_id`, полученным **из контекста**, а не из HTTP-тела.
5. Только после успешного сохранения Hub рассылает `item.created` всем подключённым вкладкам/устройствам этого пользователя.
6. React инвалидирует кэш списка и перечитывает данные через REST API.

**Важный принцип:** уведомление не хранит данные; PostgreSQL является источником истины. При переподключении клиент запрашивает список заново.

## Поток загрузки файла

1. Handler проверяет сессию, CSRF и `multipart/form-data`.
2. Размер запроса ограничивается `MaxBytesReader`.
3. Хранилище читает поток, определяет MIME по содержимому, записывает временный файл.
4. По завершении записи временный файл переименовывается в постоянное имя UUID.
5. Handler сохраняет метаданные в PostgreSQL.
6. Если запись в БД не удалась, созданный файл удаляется.
7. Уведомление WebSocket отправляется после успешной записи в БД.

**Компромисс:** транзакция в PostgreSQL и файл на диске не составляют общую атомарную транзакцию. При аварийном завершении процесса возможны осиротевшие файлы; для регулярной эксплуатации необходима процедура сверки и очистки.

## Почему нет Redis и Kafka

Hub — структура в памяти процесса с `sync.RWMutex`. Она рассылает события только между соединениями внутри **одного** процесса Go. Для нашего MVP достаточно. Redis Pub/Sub понадобился бы при нескольких экземплярах API. Очередь задач здесь не нужна.

## Где используются Go-практики

- `context.Context` — передача владельца запроса и отмена операций.
- `sync.RWMutex` — конкурентный доступ к карте WS-клиентов.
- Каналы с буфером — доставляют сообщения конкретным WebSocket-клиентам без блокировки запроса на запись в БД.
- `defer` — закрывает файлы, отменяет контексты и очищает временные ресурсы.
- `errors.Is` — отличает известные ошибки, например дубликат логина.
- `http.Server.Shutdown` — ожидает завершения обычных HTTP-запросов при SIGTERM. Активные WebSocket-соединения управляются отдельно.
- GORM `WithContext` и `Where` — фильтрация данных пользователя через ORM.
- Goose — идемпотентное применение версионированных миграций.

## Намеренные компромиссы

- Handler выполняет часть логики напрямую вместо обязательного `service` на каждое действие: отдельный слой сервисов следует вводить, когда в нём появится самостоятельная бизнес-логика, переиспользование или тестовая необходимость.
- Сессии хранятся в PostgreSQL как случайный bearer-токен, от которого сохраняется только SHA-256; это небольшая реализация вместо SCS. Перед более серьёзной эксплуатацией желательно рассмотреть проверенную библиотеку управления сессиями.
- Для списка используется `LIMIT/OFFSET`, чтобы не усложнять учебный проект. У быстро меняющегося списка возможен сдвиг страниц; при больших объёмах лучше cursor pagination.
- Нет отдельного слоя репозитория: GORM вызывается из небольших обработчиков. При усложнении бизнес-операций стоит выделить сервисы и репозитории там, где это приносит пользу.
